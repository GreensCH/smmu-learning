一句话定义：SMMU 就是「设备世界的 MMU」——CPU 访存靠 MMU 翻译地址，设备（DMA）访存靠 SMMU 翻译地址。它把设备发来的虚拟地址（IOVA）翻成物理地址（PA），并确保设备只能碰它被允许碰的内存。

你早已熟悉 MMU 的页表、TLB、缺页，SMMU 只是把这些机制搬到「设备 → 内存」这条路上。抓牢这个类比，后面所有概念都能“对号入座”。

💡 3 分钟建立直觉（先看这个，别急着抠细节）

设想你家小区（内存）有很多房间（物理页）。快递员（DMA 设备）要送货，得先把「包裹上的临时编号」（IOVA/虚拟地址）换成「真实房间号」（物理地址 PA）。SMMU 就是小区门口的传达室：它查一本登记册（页表），做编号转换，同时检查快递员有没有权限进那个房间——没登记（未映射）或没权限的，一律拦下（fault）。

这个传达室 + 登记册 + 拦截规则，就是 SMMU 的全部核心。剩下的 SteamID、STE、Stage 1/2、TLB，都是在回答三个问题：① 谁在访问？② 查哪本册子？③ 怎么翻译？

核心流程，一眼看懂

设备 →发来IOVA + StreamID →SMMU 查页表翻译 →物理地址 PA →内存

没映射 / 越权 → SMMU 报错（fault），不放行。就这么简单。

01为什么需要 SMMU：动机与价值

一句话导读没有 SMMU，设备用物理地址直接访存 = 随便进出别人家。SMMU 就是给设备装「门禁 + 地址转换」。

要“完全掌握”SMMU，先要理解它解决的根本问题。没有 SMMU 时，外设通过 DMA 直接使用物理地址访问内存，这带来三类致命问题。

① DMA 越界 / 隔离缺失

设备驱动只要写错一个 DMA 地址，设备就能读写任意物理内存（包括内核、其他进程、甚至安全世界）。一个恶意的或出 bug 的设备可以攻破整个系统。SMMU 让设备只能访问被显式映射的页。

② 虚拟化中的设备直通

虚拟机（Guest）期望以 GPA（Guest PA）使用设备，但设备 DMA 用的是 IPA/PA。没有 SMMU，无法安全地把一个 PCIe 设备直通（passthrough）给 Guest；有了 SMMU Stage 2，Hypervisor 可以把设备的 IPA 翻译到真实 PA。

③ 零散物理内存与共享页表

DMA 需要连续物理内存（如 legacy 的 bounce buffer / CMA / IOMMU 预留池）。SMMU 让设备使用连续的 IOVA（虚拟设备地址），SMMU 逐页翻译，把零散物理页拼起来，并让设备与 CPU 共享同一套页表语义。

SMMU 提供的能力清单

  • 地址转换（Translation）：把设备发起的 IOVA/GVA 翻译成 IPA/PA。
  • 访问隔离（Isolation）：未映射 / 越权访问 → 触发 fault 并 abort 或 stall。
  • 虚拟化（Stage 2）：以 VMID 为单位隔离多个 Guest 的设备访问，支持设备直通。
  • 进程级设备地址（Stage 1 + PASID/SubstreamID）：支持共享虚拟内存（SVM/SVA），设备用进程 VA 直接访问。
  • IOMMU API 统一接口：Linux 下通过 iommu_ops 抽象，驱动不关心具体是 ARM SMMU 还是 Intel VT-d。

关键结论：SMMU 与 CPU MMU 共享同一套 AArch64 页表格式，因此可以把同一份页表（或同一套描述符语义）复用给 CPU 与设备，这是 SVA（共享虚拟地址）的技术基础。

02SMMU 在系统中的位置

一句话导读SMMU 站在「设备」和「内存」之间，是设备访存的必经关卡——就像传达室必须设在小区大门口，而不是楼里。

SMMU 位于DMA 主设备与系统互联/内存控制器之间，是设备访存路径上的必经检查点。

图 1 · SMMU 的拓扑位置：CPU 用物理地址直连内存；设备的所有内存访问都经过 SMMU 完成翻译与鉴权

关键工程直觉

  • SMMU 处于事务（transaction）路径上，属于 Memory System / 一致性域（Coherency Domain）的一部分，而不是普通的“总线桥”。
  • 它对设备发出的每个 AXI/ACE/CHI 事务都必须做 StreamID → 翻译决策；因此其吞吐/延迟直接影响设备 DMA 性能，TLB 命中率至关重要。
  • 设备端发出的地址在进入 SMMU 前是IOVA（I/O Virtual Address）；进入内存控制器前必须是PA。

04核心概念与术语（务必烂熟于心）

一句话导读只需先记住两个：StreamID = 谁（哪个设备），SubstreamID = 谁的哪个进程。其余（STE/CD/ASID/VMID）都是它们“查表时用到的本子”，用到再回来查。

SMMU 的“心智模型”由下面几个概念构成。它们环环相扣，先建立整体图景。

🎯 先记住这两条，其余随用随查

  • StreamID：标识“是哪个设备”发起访问。PCIe 里通常就是 BDF（Bus:Dev.Func）。
  • SubstreamID（=PASID）：同一设备下进一步区分“是哪个进程/上下文”，用于设备同时服务多个进程（SVA）。

剩下的 STE / CD / ASID / VMID / IOVA 等，本质都是“查表和隔离”时用到的对象。想一次看清全部，展开下面的完整术语表。

StreamID 与 SubstreamID 的来源（PCIe 场景）

在 PCIe 中，事务的 Requestor ID（RID = Bus:Device.Function，16 位）由 Root Complex 转成 StreamID 送给 SMMU。若设备支持 PASID（Process Address Space ID），则 PASID TLP Prefix 转成 SubstreamID。

// 示例：NIC 直通 + 每队列一个 SubstreamID（用于 SVA）
StreamID   = 0x0088        // RID: BDF 0088 -> 设备 0000:00:88.0
SubstreamID= PASID (0..N)  // 每个硬件队列绑定一个进程地址空间

于是翻译层次非常清晰：StreamID 决定“设备级”策略（STE）→ SubstreamID 决定“进程级”策略（CD）→ 最终页表决定“页级”映射。

把 SMMU 想象成一台“以设备为主语的 MMU”：STE 是设备级页表配置，CD 是进程级页表配置，二者共同决定用哪份页表、如何翻译、谁（ASID/VMID）隔离谁。

🎯 三步口诀（记住就能复述整个流程）：

第一步“认人”——看 StreamID，找到这台设备的档案（STE）；第二步“看规则”——STE 里的 Config 决定走 Stage1 还是 Stage2；第三步“查地图”——拿页表把地址翻成物理地址。三步走完，事务放行。

06Stream Table 与 STE 详解

一句话导读STE = 每个设备的「档案卡」，回答“这个设备该怎么翻译”。Stream Table 就是一堆档案卡的抽屉，用 StreamID 当编号去翻。你只需记住最关键的一个字段：Config（决定 bypass / abort / Stage1 / Stage2）。

STE 是 SMMUv3 的“设备注册表”。每个 StreamID 一个 64 字节的 STE，软件负责在内存中维护，SMMU 按需缓存。

Stream Table 的两种索引方式

由 STRTAB_BASE_CFG 寄存器决定：

线性（Linear）

STE 地址 = STRTAB_BASE + StreamID × 64。简单直接，但表大小 = 2^SID_bits × 64，SID 位宽大时浪费内存（如 20 位 SID = 64MB）。

二级（2-level）

用 STRTAB_BASE_CFG.SPLIT 把 StreamID 分成 L1/L2 两段索引，L1 表指向 L2 子表，按需分配、节省内存。现代实现多用此方式。

STE 关键字段（64 字节 = 4 × 128bit 字）

先只记最关键的 Config 字段：它决定这个设备走哪条翻译路径（Bypass / Abort / Stage1 / Stage2）。完整字段表见下：

struct ste {                     // 64 bytes
    uint64_t word0;              // Config[2:0], S1Fmt, S1CDMax, S1STALLD ...
    uint64_t word1;              // S1ContextPtr[51:6]  (CD 表基址)
    uint64_t word2;              // S2TTB[51:4], S2T0SZ, S2SL0, S2PS, S2TG, VMID ...

要点：STE 里的 S1ContextPtr 指向 CD 表、S2TTB 直接指向 Stage 2 页表。这意味着 Stage 2 是“设备级”的（一个设备属于一个 VM），Stage 1 是“子流级”的（一个设备里多个进程各自有页表）。

07Context Descriptor（CD）详解

一句话导读CD = 每个「进程/子流」的页表配置，和 CPU 的 TTBR0_EL1/TCR_EL1 几乎一模一样。你是芯片工程师，这节对你来说就是“复习 MMU 寄存器”。

CD 描述“一个 SubstreamID 的 Stage 1 页表配置”，内容几乎与 CPU 的 TTBR0_EL1/TTBR1_EL1/TCR_EL1 语义一一对应。这是工程师最容易把 MMU 经验迁移过来的地方。

CD 字段对应 CPU 概念含义
TTB0 / TTB1TTBR0_EL1 / TTBR1_EL1用户/内核地址空间的页表基址
ASIDASID地址空间标识（16 位），用于 TLB 隔离与快速切换
T0SZ / T1SZT0SZ/T1SZTTB0/TTB1 覆盖的地址空间大小（64−T0SZ 位）
TG0 / TG1TG0/TG1页粒度：4K / 16K / 64K
SH0/SH1 / IRGN / ORGN缓存属性页表走查的内存属性（共享性、cache 策略）
EPD0 / EPD1EPD0/EPD1禁用 TTB0/TTB1 走查（enable walk disable）
AARCH64—页表格式为 AArch64（长描述符）
// 简化示意：CD 的逻辑布局（64 bytes）
struct cd {
    uint64_t word0;   // T0SZ, TG0, IRGN0, ORGN0, SH0, EPD0, AARCH64 ...
    uint64_t word1;   // T1SZ, TG1, ...
    uint64_t word2;   // TTB0[47:1]  (4K 粒度时 [47:12])
    uint64_t word3;   // TTB1 + ASID[63:48]
};

为什么这很重要：CD 与 CPU 页表寄存器语义一致，意味着可以实现 SVA（Shared Virtual Address）——设备与 CPU 进程共享同一套页表，设备直接用进程的虚拟地址访问，缺页时由 PRI 上报、内核按需分配。这是 GPU 计算、DPDK、RDMA 高性能路径的基石。

08Stage 1 / Stage 2 地址翻译

一句话导读把翻译看成两层楼梯：Stage 1 管“进程的虚拟地址”，Stage 2 管“虚拟机的中间地址”。普通系统只用 Stage 1；设备直通给虚拟机时，Stage 2 才登场。

8.1 Stage 1：VA → IPA（设备“进程页表”）

Stage 1 由 CD 描述，把设备提供的虚拟地址（VA，用于 SVA 场景，或驱动分配的 IOVA 语义）翻译成中间物理地址 IPA。非虚拟化环境（Config=0b001）中，IPA 即最终 PA。

  • 走查起点：CD.TTB0 / CD.TTB1，由 VA 高位决定用哪个基址。
  • 隔离：ASID 区分不同进程地址空间，TLB 条目带 ASID 标签。
  • 权限：页表描述符里的 AP（Access Permissions）、XN、shareability、memory type 全部生效。

8.2 Stage 2：IPA → PA（Hypervisor“虚拟机页表”）

Stage 2 由 STE 描述，把 Guest 视角的 IPA 翻译成真实 PA。这一层与 Guest 无关，完全由 Hypervisor 控制，用于设备直通时的内存隔离与映射。

  • 走查起点：STE.S2TTB，页表由 Hypervisor 维护。
  • 隔离：VMID 区分不同 Guest。
  • 关键差异：Stage 2 描述符没有 XN、没有 AP[1]（用户/内核），只有读写权限（S2AP），因为它描述的是“物理机内存对虚拟机的授权”。

09页表与走查（Page Table Walk）

一句话导读SMMU 和 CPU MMU 用同一套页表格式。地址按「层级索引 + 页内偏移」切开，一级一级查下去，最后拼接成物理地址。9.4 有个完整数值例子，建议跟着手算一遍。

SMMU 与 CPU MMU 共用 AArch64 转换表格式。理解页表走查的数学，是看懂性能、TLB、fault 的前提。

每级表大小 = 粒度大小（如 4KB 表，8 字节描述符 → 512 项 → 9 位索引）。层级数 = ⌈(输入地址宽度 − 页偏移位数) / 每级索引位数⌉；起始层级由 T0SZ/S2SL0 决定。

图 4 · 4KB 粒度 4 级走查的 VA 位域划分（每级 9 位索引 + 12 位页内偏移 = 48 位）

9.3 页表描述符（长描述符）关键位

字段含义
bits[1:0]描述符类型：0b11 = 有效（Table/Block/Page）
Table（bits[1:0]=11, bit[1]=1 且非 block/page）指向下一级表的物理地址（基址按粒度对齐）

9.4 完整实例：一个 VA 到 PA 的 4 级走查（数值推演）

下面用一个数值完全自洽的例子，把 9.2 的位域划分与 9.3 的描述符格式串起来，逐级演示从虚拟地址到物理地址的全部过程。读完这节，你就能“在纸上”完成任意一次页表走查。

📋 假设条件

  • 翻译模式：Stage 1 only（STE.Config = 0b001），非虚拟化场景，VA 直接翻译为 PA。
  • 粒度 4KB，输入地址宽度 48 位（CD.T0SZ = 16），4 级走查（L0→L3）。
  • Stage 1 页表基址来自 Context Descriptor：CD.TTB0 = 0x0000_0000_8000_0000（即 L0 表）。
  • 各级页表内容为本示例人为设定（描述符值保证与 VA 逐位对应、自洽），用于演示走查机制。

10TLB / ATC 缓存与维护

一句话导读查页表很慢，所以要缓存（TLB）。但改了页表必须“刷掉”旧缓存，否则设备还在用过期翻译。这节的灵魂就一句：改完表，记得发失效命令。

页表走查昂贵（一次可能 4 次内存访问），因此 SMMU 内部有 TLB，设备侧有 ATC。缓存一致性由“失效（invalidate）命令”维护。

10.1 三级缓存层次

① 设备侧 ATC

设备本地缓存 VA→PA，通过 ATS 协议向 SMMU 请求翻译、接收失效。离设备最近、命中最快。

② SMMU TLB

SMMU 内部缓存翻译，条目带 ASID / VMID 标签。分 stage-1-only、stage-2-only、nested 条目。

③ Walk Cache

缓存页表走查的中间节点（各级表项），加速重复走查。

10.2 缓存失效命令（CMDQ）

软件修改页表 / STE / CD 后，必须发对应失效命令，顺序通过命令队列保证。

命令作用典型触发时机
CMD_CFGI_STE / CFGI_STE_RANGE失效 SMMU 缓存的 STE修改设备 STE 配置后
CMD_CFGI_CD / CFGI_CD_ALL失效缓存的 CD修改某进程 CD 后
CMD_CFGI_ALL失效全部配置缓存粗粒度全局失效
CMD_TLBI_NH_VA / TLBI_NH_ASID按 VA / ASID 失效 Stage1 条目进程页表 unmap 后
CMD_TLBI_S2_IPA按 IPA 失效 Stage2 条目Hypervisor 改 Stage2 映射
CMD_TLBI_S12_VMALL失效某 VMID 的所有嵌套条目VM 整体失效
CMD_ATC_INV失效设备侧 ATC同步远端设备缓存
CMD_PRI_RESP / CMD_RESUME响应 PRI / 恢复 stall 的事务缺页处理完成后

⚠️ 经典 bug 模式

修改了页表/STE/CD 却忘记发失效命令，导致 SMMU TLB 或设备 ATC 仍用旧翻译 —— 表现为偶发数据错乱 / 访问到已释放的内存。Linux 的 iommu_map/unmap 会在背后正确完成 flush，但自研裸机/BSP 代码必须显式处理。

11命令 / 事件 / PRI 队列

一句话导读SMMU 和软件靠三条“传话管道”沟通：命令队列（软件→SMMU 下指令）、事件队列（SMMU→软件报错）、PRI 队列（设备缺页时求助）。都是内存里的环形缓冲区。

SMMUv3 用内存中的环形队列与软件交互（而非大量 MMIO 寄存器）。理解三队列是理解驱动实现的关键。

命令队列 CMDQ

软件 → SMMU 的控制通道。软件写入命令（16 字节/条），更新 PROD 指针；SMMU 消费并更新 CONS。命令包括 TLBI、CFGI、ATC_INV、PRI_RESP 等。

事件队列 EVENTQ

SMMU → 软件的错误/事件上报（32 字节/条）。包括 STE/CD 获取错误、翻译 fault、权限 fault、不可恢复错误等，配合中断通知软件。

PRI 队列 PRIQ

设备 → SMMU → 软件的缺页请求（16 字节/条）。设备遇缺页时经 PRI 上报，软件分配页、更新页表后用 CMD_PRI_RESP 回应，实现按需分页。

队列环形结构

// 环形队列：BASE 指向队列基址，PROD/CONS 为生产者/消费者下标
      BASE  +----+----+----+----+ ...
            | cmd| cmd| cmd|    |     ← 软件写 PROD，SMMU 读 CONS
            +----+----+----+----+
  PROD ──> 待写入位置           CONS ──> 待消费位置

事件类型速查

事件含义
EVT_C_BAD_STREAMIDStreamID 无有效 STE（越界）
EVT_C_BAD_STE / C_BAD_CDSTE / CD 配置非法或获取失败
EVT_F_TRANSLATION页表走查翻译失败（如缺映射）
EVT_F_ADDR_SIZE地址超出范围（如 VA 位宽超 T0SZ）
EVT_F_ACCESS / F_PERMISSIONAF=0 / 权限不足（读写越权）
EVT_F_UUT不可恢复 / 不支持的事务
EVT_F_WALK_EABT页表走查本身发生外部 abort

12寄存器与编程模型

一句话导读SMMUv3 把「大块数据」放进内存（表、队列），寄存器只留「几个指针 + 开关」。初始化就是：分配表 → 填指针 → 使能，故障处理就是「读事件队列」。

SMMUv3 把大量状态放进内存结构，MMIO 寄存器只负责“入口”：指向 Stream Table 与各队列、控制使能、上报全局错误。

12.1 核心寄存器（SMMUv3，偏移为基址内偏移）

// 6. 挂接中断，处理 EVENTQ 上报的 fault

12.3 Fault 处理流程

  1. 事务触发 fault → SMMU 把事件写入 EVENTQ，更新 PROD，触发中断（若使能）。
  2. 软件读 CONS，解析事件类型与地址（STE/CD 错误 or 翻译/权限错误）。
  3. 可恢复 fault：修复页表（如分配页）→ 发 CMD_TLBI_* 失效 → 恢复事务。
  4. 不可恢复 fault：记录日志、复位/隔离设备（如把 STE 置为 Abort）。
  5. 更新 CONS，处理下一个事件。

13Linux 内核实现（实战视角）

一句话导读Linux 用一套统一的 IOMMU API 把 SMMU 抽象掉，驱动只做三件事：建页表、下发命令、处理故障。看懂 arm-smmu-v3.c 就懂了 SMMU 工程实现。

Linux 主线的 SMMUv3 驱动位于 drivers/iommu/arm/arm-smmu-v3/，通过 IOMMU API 暴露统一接口。理解它能把前面的理论落到代码。

14调试与性能

一句话导读SMMU 出问题，九成是：① StreamID 没映射 ② 忘了失效缓存 ③ Stage2/VMID 配错。遇到 DMA 数据错乱，先查这三样。

14.1 常见故障排查清单

现象可能原因排查手段
设备 DMA 数据错乱 / 读到旧数据页表/STE/CD 修改后未失效 TLB/ATC检查 CMD_TLBI/ATC_INV 是否缺失

14.2 性能要点

  • 大页（huge page）：用 2MB/1GB 映射降低走查层级与 TLB 压力。
  • 页表走查缓存属性：走查本身的内存也要正确配置 cacheable，否则走查极慢。
  • ATS：启用设备侧 ATC 可显著降低 SMMU TLB 压力，但需正确维护失效。
  • 队列深度与中断合并：CMDQ/EVENTQ 深度与中断节流影响吞吐。
  • 减少 flush：批量化 map/unmap，用 range 型失效命令。

15常见误区与易错点

一句话导读这 6 个坑是工程师踩出来的，每条都对应前面某一节。考前快速过一遍，能帮你避开 90% 的实战问题。

① 把 StreamID 当成“设备编号”随意分配

StreamID 必须与系统拓扑（PCIe RID / IORT）一致，否则设备会命中错误的 STE。它本质是“事务请求者的路由身份”。

② 混淆 Stage 1 与 Stage 2 的地址语义

Stage 1 输入是 VA、输出 IPA；Stage 2 输入 IPA、输出 PA。嵌套时中间是 IPA，不是“两次 PA”。

③ 认为 Bypass 是安全的默认值

Bypass 让设备直通物理地址，等于无隔离。生产环境默认应为 Abort，只有明确信任的设备才 Bypass。

④ 忘记缓存失效的“范围与顺序”

不仅要失效 SMMU TLB，还要失效设备侧 ATC（CMD_ATC_INV），并保证命令按序生效。

⑤ 页表与 CPU 不共享时属性不一致

设备与 CPU 对同一物理页的内存属性（cacheable/shareable）不一致会导致 coherency 问题。

⑥ 忽略 Stage 2 无“用户态”概念

Stage 2 描述符只有读写权限（S2AP），没有 XN 与用户/内核区分——它表达的是 Hypervisor 对 Guest 的授权。

  • ARM SMMUv3 架构规范：IHI 0070（System Memory Management Unit Architecture Specification）—— 最权威的位域与行为定义。
  • ARM 架构参考手册（ARM ARM）：DDI 0487，第 D5 章（AArch64 地址翻译）—— 页表走查、描述符位域。
  • Linux 内核源码：drivers/iommu/arm/arm-smmu-v3/、drivers/iommu/io-pgtable-arm.c —— STE/CD/命令/事件位域与驱动实现。
  • PCIe 规范：ATS（Address Translation Services）、PRI（Page Request Interface）、PASID 章节。
  • Intel VT-d 规范：用于对照 IOMMU 概念（Root Table / Context Entry / PASID）。

🎯 最终检验标准（“完全掌握”的标志）

你能独立回答：① 一个 PCIe 设备发起的 DMA 事务如何一步步走到物理内存？② 如何让该设备安全直通给一个 VM？③ 如何支持该设备使用某进程的虚拟地址（SVA）？④ 修改页表后为何要、以及要发哪些失效命令？⑤ 一个翻译 fault 从发生到被内核处理的完整链路是什么？——若都能答出，即已掌握 SMMU。
